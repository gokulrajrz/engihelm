# Risk-scaled SDLC operating modes: less process, same honesty

Apply to **every task**, including Orchestrator-owned items. Choose the smallest mode justified by observed impact, not by a desire to avoid work. Every agent records a factual update in the same local SQLite tracker; use no Jira or GitHub Issues. Modes are documentation/review budgets, **not exemptions** from acceptance verification, secure implementation, source inspection, authorized actions or truthful claims. A task may be raised to a higher mode but never downgraded below its observed risk.

| Mode | Appropriate examples | Minimal artifacts and proof | Staffing/review |
| --- | --- | --- | --- |
| `small` | Isolated reversible typo, low-risk test or trivial local fix with no data/security/interface implications | One concise descriptive tracker record, acceptance IDs, one compact root ledger with `ROOT-TRACK` and acceptance evidence; use `lightweight` for explicitly advisory manual checks, or `local` with a real focused executable receipt for machine-checked completion, final reconciliation | Implementing agent or Orchestrator; same-context recheck may be disclosed, no fabricated independent review. No ceremony/ADR/PRD/TSD by default. |
| `standard` | Routine feature/bug involving behavior, a component or known interfaces, normal regression risk | Task tracker, concise scope/contract plan, relevant acceptance gates and implementation tests, full root ledger gates, executable evidence linking tasks to ledger, integration where applicable | Relevant implementer and a distinct reviewer for verified task closure (the local checker requires an identifiable reviewer different from the owner); if unavailable, retain an unfinished/partially verified state and explain why. Route to QA or specialty only if needed. |
| `high-risk` | Authentication/authorization, secrets/PII, destructive or irreversible data changes, migration with material blast radius, payment/access entitlement, production incident, high-risk infrastructure/release | Detailed requirements, design/rollback and security/risk analysis proportional to blast radius; all root gates, independent review evidence, approved execution policy, signed receipt with externally isolated signer, documented authorization where required | Relevant engineers plus genuinely separate security/QA/release review where risk warrants; explicit authorized approval for dangerous or irreversible steps. |

## Mandatory escalations

Raise to `high-risk` for changes to auth/permissions, sensitive data handling, irreversible migration, externalized secrets, critical operational safety or high-impact production deployment. Raise to at least `standard` for public contracts, concurrency, multi-component integration, user-visible behavior and nontrivial refactoring. If evidence of risk is ambiguous, do not silently choose `small`; inspect and record the decision. A reviewer can escalate, never silently waive required checks. **Limit:** The verifier can compare the ledger tier with the recorded SQLite risk tier, but cannot determine whether an agent underreported actual security/data/operational risk. Risk classification needs code inspection and independent review for sensitive areas; a self-declared `small` flag is not a security boundary.

## Anti-overhead rules

- Track **meaningful milestones and blockers**, not every shell command. One detailed task can encompass a small change; split only independent work with a real acceptance boundary.
- Use the same SQLite state + generated `TASKS.md`; do not create parallel spreadsheets, shadow boards or duplicate ledgers. For a small task, a root ledger containing the real acceptance gates and `ROOT-TRACK` can serve as its entire assurance record. Standard/high-risk retain full root coverage and only actual specialist leaf ledgers.
- Do not require Scrum ceremonies, architecture decision records, sprint reports, TSDs, threat models, full test suites, independent specialist teams or multi-agent dispatch for low-risk isolated work unless specific requirements demand them.
- For standard work, prefer **one implementer plus one genuinely distinct reviewer** to satisfy the local completion gate, not 14 agents; if independent review is unavailable, report partial/blocked status rather than marking Done. Reuse existing project documentation and tests instead of restating them.
- Targeted tests first; full or additional checks when behavior, integration or blast radius warrants it. Never replace relevant tests with lint solely to save tokens.
- Avoid perfunctory reruns after unchanged results in the same verified revision. Rerun if source, policies, requirements, or relevant environment changed; document the evidence and the verification context.
- Agent budget rules may trim context, parallelism and redundant reviews but must **not** weaken high-risk authorization or executable proof.

## Unified final decision

Before asserting verified code completion, invoke `scripts/completion_decision.py` with the SQLite DB, actual Git revision, root/leaf ledgers, reviewed policy pin and one exact gate-runner receipt. Small, low-risk work may use `--mode lightweight` without policy/receipt; that returns only `LIGHTWEIGHT_DECLARED` and must NOT be represented as executed or independently verified. It checks for missing tasks and requirements, stale or unrelated evidence, under-tiered root ledger, required root gates, unsigned high-risk receipts, unresolved work and false completion claims. See `references/enforcement.md`. A `LOCAL_CONSISTENT` result remains **local observation**; `SIGNED_RECEIPT_MATCH` verifies receipt cryptography, **not** external isolation or the truth of manual review assertions. If a host lacks executable tools or persistence, report `PARTIAL/UNVERIFIED` without manufacturing a pass.

**State transition rule for every tier:** use `verify_and_close.py` to close a Verified SQLite task; do not use direct `transition --state Done`. The small tier remains explicitly `LIGHTWEIGHT_DECLARED` when no real executable receipt is supplied; do not advertise it as independent verification.
