# Durable project-local orchestration and safe recovery

Use `docs/sdlc/state.db` (SQLite) as the **only authoritative local task store** and its auto-regenerated `docs/sdlc/TASKS.md` as the readable snapshot. Do not connect Jira, GitHub Issues or other external issue-management systems. JSON templates are legacy local fixtures, not a parallel board. The database records task owner, state, narrative scope/outcome/acceptance, progress, blockers, dependencies, next action, evidence refs, commit, reviewer and transactional journal events.

- A **new project** uses `python <skill-root>/scripts/state_store.py --db docs/sdlc/state.db init` once. Initialization refuses to overwrite an existing DB or recreate one if a prior project marker or TASKS report survives. It makes a project identity manifest. Work items require clear descriptions and acceptance details, not title-only rows.
- Every mutation of tasks creates an event and increments its version. Stale `--expected-version` fails instead of overwriting other agents. `amend` invalidates old evidence after scope changes. `migrate` is an explicit, additive schema upgrade for pre-existing SQLite state; back up the file outside the tool before running it.
- `resume` shows all unresolved tasks; `show` shows the full structured store. The generated Markdown contains a summary table, outcome/context, acceptance, approach, completed/remaining work, blocker, decisions, verification and recent history. The view is not authoritative and is regenerated after mutations.
- `verify` checks local event-chain consistency; `audit` additionally rejects unresolved items, missing descriptive fields and incomplete closure links. Neither authenticates referenced evidence nor proves that an agent could not tamper with the database.
- `backup --output DEST` takes a SQLite-consistent snapshot, validates local integrity and copies the project manifest; store backups in a protected location as appropriate. `restore --from BACKUP` requires a missing destination database, a surviving project manifest, the matching backup manifest and valid SQLite/journal state. It cannot recover unbacked-up work. Check actual Git/evidence revisions after restore.
- **Missing DB, no surviving marker:** the tool says first-run initialization may be appropriate but warns that prior state could have been lost. Require a real project-history check before `init`; absence of files is not proof of new work.
- **Missing DB, surviving marker/report:** fail closed; do **not** auto-init. Restore a verified project backup or report blocked/data loss. If both DB and marker are missing but known work existed, seek manual recovery and never fabricate task states.

For parallel agents, the Orchestrator coordinates one authoritative writer or deliberately uses optimistic revisions. Avoid DB files committed to a repository when they contain sensitive operational content; ensure backups and permissions follow project policies. SQLite WAL is a consistency mechanism, not an access-control boundary. A generated report alone is insufficient for recovery.

**Guarded closure:** Never use `state_store.py transition --state Done`. Each task must reach `Verified` with current Git/evidence references, then the Orchestrator calls `scripts/verify_and_close.py` with a task-scoped COMPLETE root ledger and expected task version. Missing/invalid proof leaves the task Verified or blocked. The local receipt and reviewer fields are not authenticated human authority.
